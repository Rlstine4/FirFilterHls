# Accelerated FIR Filter (Vitis HLS 2026)

Free-running streaming FIR filter for AMD/Xilinx Zynq UltraScale+ / RFSoC in Vitis HLS.

- Taps: real `coeff_t = ap_fixed<16, 2>`, runtime programmable over AXI4-Lite.
- Samples: complex I/Q, `sample_val_t = ap_fixed<16, 2>` for real and imaginary.
- Bus: one AXI4-Stream beat carries `SSR` complex samples, width = 32 * SSR bits
  (SSR=1 -> 32, SSR=2 -> 64, SSR=4 -> 128, SSR=8 -> 256 bits).
- Rate: `II=1`, one beat in and one beat out per clock, all taps unrolled.
- Control: `ap_ctrl_none`, so the block free-runs with no start/done handshake.
- Tap updates are atomic: `save_config()` copies the whole tap set in one cycle
  when the processor toggles `write_config`.

## Module structure

| Element | File | Role |
| --- | --- | --- |
| `FirConfig` | `FirFilter.hpp` | AXI4-Lite shadow register map: `taps[NUM_TAPS]` plus the `write_config` toggle |
| `ActiveConfig` | `FirFilter.hpp` | Committed coefficient set actually used by the datapath |
| `save_config()` | `FirFilter.hpp` | Grabs a new tap set from the AXI4-Lite registers; copies all taps in one cycle |
| `config_toggled()` | `FirFilter.hpp` | Detects a `write_config` toggle, i.e. a commit request |
| `FirFilterCore::process()` | `FirFilter.hpp` | All filter logic for exactly one beat; no frame or packet counts |
| `FirFilter()` | `FirFilter.cpp` | Top-level module; free-running beat loop, calls `save_config()` and `process()` |

## Interfaces

| Port | Interface | Description |
| --- | --- | --- |
| `in_stream` | AXI4-Stream slave | Input beats of `SamplePacket` (`32 * SSR` bits) |
| `out_stream` | AXI4-Stream master | Output beats of `SamplePacket` (`32 * SSR` bits) |
| `axi_cfg` | AXI4-Lite `control` | `FirConfig` shadow registers |
| `return` | `ap_ctrl_none` | No start/done handshake, block free-runs |

## Tap update protocol (tear-free)

1. Write `taps[0 .. NUM_TAPS-1]` to the AXI4-Lite registers.
2. Toggle `write_config`.

`save_config()` keeps the committed `ActiveConfig` separate from the AXI4-Lite
shadow registers. A new tap set is adopted only on a `write_config` toggle, and
all `NUM_TAPS` coefficients are copied in a single clock cycle. In-flight samples
therefore never observe a partially written coefficient set.

The first beat always adopts the register contents, so a driver may either
pre-load taps and leave `write_config` alone, or pre-load taps and toggle.

## Usage

`build.py` regenerates `hls_config.cfg` with the requested compile-time
parameters and then runs the selected flow.

```bash
# Host C++ simulation (works before Vitis HLS is installed, uses .hls_compat)
python3 build.py host_sim --num-taps 8 --ssr 4 --beats 128

# Vitis HLS C simulation
python3 build.py csim --num-taps 8 --ssr 4

# Vitis HLS C synthesis
python3 build.py csynth --num-taps 8 --ssr 4

# C/RTL co-simulation (add --trace for waveforms)
python3 build.py cosim --num-taps 8 --ssr 4 --trace

# Vivado implementation
python3 build.py impl --num-taps 8 --ssr 4

# Everything: csim, csynth, cosim, impl
python3 build.py all --num-taps 8 --ssr 4
```

`--beats` is a testbench parameter only; it sizes the simulated frame and is not
a kernel port. In synthesis the beat loop is `while (true)`; for host sim and
C simulation it is compiled as a bounded loop of `NUM_BEATS` beats.

Notes on the tool flow: in Vitis HLS 2024.x and later the Tcl flow
(`vitis_hls -f script.tcl`) is replaced by `hls_config.cfg` driven by
`v++ --compile --mode hls` for synthesis and `vitis-run --mode hls --csim`,
`--cosim`, `--impl` for the other stages. `build.py` wraps those calls.
